# Security review — 16 October 2026

This review covers the running Express API, frontend modules, image delivery, storage integrations and Compose configuration. It is a source review and regression pass, not a claim that a deployed service has no vulnerabilities.

## Fixed

- Validation failures no longer print submitted bodies or passwords to logs. Validation responses contain only field names and messages.
- Logout and password changes revoke access tokens immediately through an account session version. Refresh tokens rotate with a compare-and-swap database write so concurrent replay succeeds at most once. JWT verification restricts the algorithm and validates identity/role/version claims; media cookies cannot act as API bearer tokens. Session restoration/sign-out do not consume the stricter credential-attempt limit and remain covered by the general API rate limit.
- Refresh tokens now live in HTTP-only, same-site cookies; JavaScript keeps only an in-memory access token. Production cookies require HTTPS. Legacy session storage is removed when migrating an existing session.
- New passwords require 12 characters, reject common/repeated values, and are limited to 72 UTF-8 bytes to prevent bcrypt's silent truncation, including with Bengali characters. Existing login passwords remain accepted within the prior input bound. Error responses no longer expose stack traces or unexpected internal errors, including in development.
- Optional authenticator verification protects both reader and team accounts. Secrets use authenticated encryption, accepted time steps cannot be replayed, and eight recovery codes are hashed and consumed atomically. Setup confirmation, replacement recovery codes and disabling MFA require the current password; existing MFA also requires an authenticator or recovery code. Persistent per-account limits also cover password changes and security reauthentication. Security changes revoke active sessions. MFA remains enabled after password recovery.
- Reader/team password recovery uses random, hashed, expiring, single-use links. Atomic reset writes prevent two requests from consuming the same link. Reader username reminders disclose usernames only through email. Recovery responses are generic and time-padded; a bounded email queue decouples mail transport from responses. Persistent per-identity attempt limits, per-account recovery cooldowns and IP limits restrict abuse. This does not make public usernames or registration availability secret.
- Recovery links use the configured trusted public origin and URL fragments, never the request Host header. Password/username recovery is unavailable with an explicit setup message when SMTP is unconfigured. Security notices omit passwords and codes. Recent account activity retains only a masked network and a bounded browser identifier, expiring after 30 days.
- Personal settings and imported device backups use allowlists and bounds. Backups exclude account credentials, tokens and email addresses. Readers can pause new history activity while retaining chapter progress.
- JSON, URL-encoded and multipart request fields reject MongoDB operator/prototype keys and excessive nesting. Pagination is bounded. Chapter page edits reject malformed entries and do not accept arbitrary new file references.
- Draft series/chapter previews require publishing permissions. Media reads apply chapter and parent-series rules before touching a provider. Upload listings respect the actor's content permissions. History/follows no longer populate hidden series or unpublished chapters.
- Google Drive uploads no longer grant public sharing. Public/domain-shared destination folders are refused. The studio can revoke legacy public sharing and replace direct links with protected application URLs. A Drive connection with active images cannot be deleted.
- S3 uploads use opaque keys and protected application URLs, without requesting a public ACL. Production endpoints must use HTTPS. Reads reject oversized objects and arbitrary object paths. Provider credentials remain on the server.
- Newly stored Drive credentials use AES-256-GCM authenticated encryption and fail closed on ciphertext authentication failure. Legacy CBC records remain readable for migration. There is no built-in fallback encryption secret.
- Admin upload policy is enforced before provider writes. Existing signature checks, 10 MB image/80 MB archive/200 page bounds, compressed archive checks and replacement/deletion guards remain. Multipart field sizes/counts and concurrent upload staging are bounded.
- Team mutations are audited for 90 days without bodies, credentials or query strings. The owner cannot demote or deactivate their own account through the team editor.
- Compose now configures database authentication and a separate application database user, keeps database ports internal and binds the web port to loopback for a reverse proxy.
- SEO template replacements treat dollar-sign replacement sequences literally as well as escaping HTML.

## Validation

The build, 14 frontend tests, 66 backend tests, 21 catalog/storage database integration checks and 18 authentication database integration checks pass. Regressions cover authorization, token revocation/replay, private remote media, multipart injection, encryption tampering, S3 operations, Drive folder privacy and graceful startup failure. Authentication checks exercise password-reset races, hashed expiring tokens, generic username reminders, cookie rotation, MFA challenges/replay, single-use recovery codes, factor-preserving resets, team-account isolation and attempt limits. Integration checks use disposable databases and temporary media; SMTP is captured locally and provider calls are mocked. The actual catalog is not seeded with test content and the owner's credentials/MFA are not changed.

Server-disk images retain streaming delivery. Remote media transfers are bounded to eight per process and upload staging to two concurrent requests; S3 connections are reused across image operations.

The production npm dependency audit returned zero known vulnerabilities. Results are a point-in-time dependency check, not a guarantee against unknown issues.

## Deployment boundaries

- No cloud-storage credentials were supplied: S3 and Drive request paths are covered by mocked-provider tests; live provider permissions, bucket policy and inherited Drive sharing still require the studio's connection/security checks with your account. S3 buckets must remain private. Disabling a storage account or changing its bucket/prefix can make existing media unavailable.
- SMTP, Docker execution, external TLS/reverse-proxy configuration and deployed CORS behavior were not exercised. Provision users before enabling authentication on an existing Compose volume; never delete persistent data to perform that change.
- Keep environment files, database files and uploaded media out of Git. Configure strong distinct JWT secrets, back up stable storage/auth encryption keys, use HTTPS and set CLIENT_URL and PUBLIC_URL to the real website origin. Set proxy trust only for a known deployment topology. Do not rotate AUTH_ENCRYPTION_KEY without migrating stored authenticator secrets; when omitted, it follows JWT_SECRET.
- The browser expects a same-origin API so strict refresh cookies work reliably. Cross-site frontend/API hosting requires an intentional cookie/CSRF design, not simply broadening CORS. MFA is optional and must be enabled by each account owner.
- The bounded SMTP queue is in memory: a process restart can lose pending mail. A durable queue and distributed IP rate limiting are deployment improvements for multiple replicas; account attempt limits already persist in MongoDB. Monitor delivery failures and provide operational support for lost factors.
- The application currently maintains one rotating refresh session per account; a new login replaces the previous refresh/media session. Guest page bookmarks are device-local and can be exported from Saved pages.
